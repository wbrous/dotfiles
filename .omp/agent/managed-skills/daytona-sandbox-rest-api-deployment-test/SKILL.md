## Setup recap (unchanged from before)

1. `POST https://app.daytona.io/api/sandbox` with `{"snapshot": "<name>"}` — pass `"autoStopInterval": 0` if the sandbox needs to stay up for a human to interact with it later (default auto-stops after 15 min idle, which would kill a "leave it running for the user" deployment).
2. Poll `GET https://app.daytona.io/api/sandbox/{id}` until `"state":"started"`.
3. Upload files: `POST https://proxy.app.daytona.io/toolbox/{sandboxId}/files/upload?path=<dest>` with `-F "file=@<local path>"`. Uploads are occasionally flaky (curl exit/HTTP code `000` with no error text) — always check the HTTP code and retry the specific file once if it happened; don't assume the whole batch failed.
4. Run commands: `POST https://proxy.app.daytona.io/toolbox/{sandboxId}/process/execute` with `{"command": "...", "timeout": <seconds>}`. `timeout` in the JSON body caps server-side execution; also set `curl --max-time` a bit higher than that. Long-running installs (apt, docker compose pull) routinely take 30-90s — this often triggers the bash tool's own backgrounding; just `hub wait` for it, don't poll manually.
5. Container-class sandboxes have `PID 1 = daytona`, not systemd (`ls /run/systemd/system` → No such file). Any bootstrap script step that does `systemctl enable --now X` will fail with `System has not been booted with systemd as init system (PID 1). Can't operate.` — this is expected on this sandbox class and is not a bug in the script. Docker itself installs fine via apt; to actually use it, start it manually: `nohup dockerd >/tmp/dockerd.log 2>&1 & disown; sleep 4; docker version`. Nested/nested-in-nested Docker (docker compose running inside the sandbox) works fine this way.
6. Teardown: `docker compose down -v` inside the sandbox first (if you care about clean removal, otherwise skip), then `DELETE https://app.daytona.io/api/sandbox/{id}?force=true`.

## Exposing the deployed service for live human interaction

When the deliverable is "leave it running so I can connect to it" (as opposed to a one-shot verification run), the deployed app is typically bound to `127.0.0.1:<port>` inside the sandbox's own compose network — reachable from *inside* the sandbox via `curl http://localhost:<port>`, but not directly from the outside internet. Daytona's preview URL mechanism is the way to expose it:

- **Standard preview URL** (`GET /api/sandbox/{id}/ports/{port}/preview-url`) returns a URL plus a sandbox-wide token that must be sent via the `x-daytona-preview-token` header. This token authenticates *every* port on the sandbox (web terminal 22222, toolbox API, etc.) — treat it as a full sandbox credential, not a scoped viewer token, and don't hand it to the end user as "click this link."
- **Signed preview URL** (`GET /api/sandbox/{id}/ports/{port}/signed-preview-url?expiresInSeconds=<n>`) embeds the auth token directly in the *hostname*: `https://{port}-{token}.{daytonaProxyDomain}`. No header needed — this is safe to hand directly to a human as a clickable link, is scoped to one port, and can be revoked/expires independently. Use `expiresInSeconds` up to 86400 (24h max); always set it explicitly (default is only 60s).

**Critical gotcha discovered empirically**: if the deployed app makes its own internal self-referencing HTTP calls using a "public URL" config value (e.g. Logto's `ENDPOINT` env var, used for OIDC discovery self-consistency, JWKS, etc.), that config value **must be set to the exact signed preview URL**, not `http://localhost:<port>` and not a plain public-looking placeholder. Reasoning:
- If left as `localhost`, the app's own emitted URLs (issuer, endpoints in the discovery doc) won't match what the external caller (browser or curl) actually used to reach it, breaking any client that validates issuer match.
- If set to a *standard* (non-signed) preview URL, the app's own outbound self-calls to that URL will get rejected by Daytona's proxy (401/warning page) because they won't carry the `x-daytona-preview-token` header — mirroring the exact same "internal self-call breaks because the endpoint value points at a proxy hop requiring auth the internal caller doesn't send" failure mode documented for Logto's `ADMIN_ENDPOINT`/`ENDPOINT` split in the phermata/optic-fyi identity service (see `docker-compose-required-env-var-colon-quoting` and identity decisions doc).
- Setting it to the **signed** preview URL fixes both problems: the token is baked into the hostname itself, so both the app's own internal fetches and the human's browser hit the exact same, already-authenticated URL — verified end-to-end (curl from outside the sandbox to `/oidc/.well-known/openid-configuration` returned `200` with the issuer correctly showing the signed preview hostname).

Concrete flow that worked:
1. Get the signed preview URL for the port *before* writing the app's `.env`/config (`GET .../signed-preview-url?expiresInSeconds=86400`).
2. Write that exact URL into the app's public-endpoint config (e.g. `sed -i 's|^ENDPOINT=.*|ENDPOINT=<signed url>|' .env`).
3. Bring the stack up.
4. Verify from *outside* the sandbox (plain `curl`, no special headers) that the service responds correctly and that any self-reported URLs (issuer, discovery doc, etc.) match the signed preview hostname.
5. Hand the plain signed preview URL to the user as the connection link.

Also tell the user explicitly: which port(s) are intentionally *not* exposed (e.g. an admin console meant to stay private per the design), the token's expiry time, and that the sandbox has `autoStopInterval:0` so it won't silently die from idleness — but it also won't survive a Daytona-side restart/outage, so if asked to redo the whole thing later, just recreate the sandbox from scratch rather than trying to recover a stale ID.
