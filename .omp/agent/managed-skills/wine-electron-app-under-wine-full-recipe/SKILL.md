## Symptom triage (run these first, in order)

1. **No window ever appears, process dies ~15-17s after launch, no coredump, no signal.**
   Track precisely with a polling loop (not a fixed sleep) — grep for the literal exe name across `ps -eo cmd` every second for 25s, and separately check `hyprctl clients -j | jq` (or grep) for the window class every second. A single `procs=N` count from `grep -c` is unreliable: it matches parent AND every `--type=gpu-process/renderer/utility` child, so "procs=1 sustained" can hide the real main process dying and being replaced by an orphaned child. Always disambiguate main vs child via full cmdline.
   - Root cause found here: **GE-Proton's wine-staging build's Chromium/Electron mojo IPC handshake between main and child (gpu/renderer/network) processes never completes** — hits Chromium's `ChildThreadImpl::EnsureConnected()` 15s connection timeout (see it via `ELECTRON_ENABLE_LOGGING=1 wine app.exe --enable-logging=stderr --v=1`, grep for `EnsureConnected`), then the whole app silently exits. This is NOT fixed by `--no-sandbox` or `--single-process` (single-process actually made it crash even faster/harder). Fix: use **plain system wine** instead of GE-Proton for Electron/Chromium-based Windows apps (GE-Proton is tuned for DirectX games, not needed here and actively worse for this IPC path). Rebuild a fresh `.pfx` with `wineboot --init` under system wine and point `launch.sh`'s `PATH`/`WINEDLLPATH`/`LD_LIBRARY_PATH` at nothing extra (just plain `wine`).
   - A second, unrelated crash cause with an identical-looking silent death: **Wine's `windows.ui.dll` / `IUISettings2::get_TextScaleFactor` is a stub that recurses until stack overflow**, killing whichever thread calls it (visible as `err:virtual:virtual_setup_exception stack overflow ... addr 0x70...` in the log, sometimes preceded by thousands of repeated `fixme:ui:uisettings2_get_TextScaleFactor ... stub!` lines). Fix: `export WINEDLLOVERRIDES="windows.ui=d"` in the launch script — forces `RoGetActivationFactory` to fail cleanly for that WinRT class instead of looping, and Electron/Chromium falls back to a default text scale.
   - Both fixes are independent and can both be needed simultaneously (this app needed both: plain wine AND the dll override).
   - Diagnostic dead ends to skip next time: `coredumpctl list` (no entry — it's a clean exit, not a signal), checking for Crashpad `.dmp` files under the app's `AppData/Roaming/<App>` (Crashpad handler itself doesn't spawn correctly under Wine so no dumps are ever written), `strace` (often not installed, don't rely on it being available).

2. **Window shows up but all text is missing / small black boxes where icon-font glyphs should be.**
   Check `find "$WINEPREFIX/drive_c/windows/Fonts" -maxdepth 1 | wc -l` — if it's `1` (just the dir itself), the prefix has **zero fonts installed**. `wineboot --init` does NOT install any TTF fonts by default. Fix: `winetricks -q corefonts` against that `WINEPREFIX` (takes ~100s, run backgrounded via `hub`/nohup and wait on it). This single fix explains both "no text renders anywhere" (no font to rasterize glyphs with) AND "small black box in header" (a tofu/missing-glyph render for an icon-font character, e.g. a hamburger-menu icon rendered via an icon font). Don't chase a separate "black box" theory (broken PNG alpha, GPU compositing bug, etc.) before ruling this out — it's a one-line fix and was the actual full explanation here.

3. **Bottom of the app / toolbar buttons clipped off-screen, resizing doesn't help.**
   If the app is Electron and NOT packaged in an `.asar` (check `resources/app/main.js` exists as a plain readable file, not inside `resources/app.asar`), you can edit its `main.js` directly — no repackaging needed, changes take effect on next launch.
   - First check for a persisted window-bounds config (commonly via `electron-store`, stored at `$WINEPREFIX/drive_c/users/<user>/AppData/Roaming/<App>/config.json` with a `winBounds: {x,y,width,height}` key). A prior crashed/buggy run can persist garbage bounds (e.g. negative `y`, `width`/`height` larger than the actual display workarea) that push the window off-screen or oversize it, clipping the bottom permanently even after "fixing" other things. Delete that key/file as an immediate fix.
   - For a durable fix, edit the `BrowserWindow` constructor call in `main.js` (search for `new BrowserWindow(`) to stop trusting saved bounds blindly and instead **always compute `width`/`height` as a fraction (e.g. 0.95) of `require('electron').screen.getPrimaryDisplay().workArea`**, centered (`x = area.x + (area.width - width)/2`, same for y), and leave `resizable: true` untouched so the window still responds normally to manual resizing/tiling-WM management afterward. Don't just clamp saved bounds to 100% of the workarea — window-frame/decoration overhead under Wine can still push the effective content past the visible area at exactly 100%; 95% leaves real margin. If a `config.set('winBounds', ...)` persistence call exists elsewhere (e.g. in a `window.on('close', ...)` handler), it's fine to leave it as dead-ish future-reference state even if load-time no longer reads it — don't remove the electron-store `Config` instance if anything else in the file still calls `.set()`/`.get()` on it (grep for `config\.` before deleting the variable).

## General workflow notes for this whole app class
- To pass Chromium/Electron command-line switches to a packaged Electron app, you often CANNOT rely on `argv` — many apps (this one included) have custom command-line parsing in `main.js` that only recognizes a fixed set of `--known-flag` patterns and silently treats anything else as a file path to open (logs `Attempt to load file --your-flag` / `Cannot open file`). If `main.js` is unpacked/editable, add `app.commandLine.appendSwitch(...)` calls directly in the source near other existing `app.commandLine.appendSwitch(...)` calls (there's usually already at least one, e.g. for `ignore-gpu-blacklist`) instead of trying to get flags through argv.
- Always verify window state with a **timed polling loop** (`for i in $(seq 1 25); do sleep 1; check...; done`) rather than a single `sleep N && check` — timing of process spawn/death/window-map is not instantaneous and single-point checks miss real transitions (main process dying vs. child surviving, etc).
- To actually SEE a Wine app's rendered window instead of guessing from logs, screenshot it via `hyprctl clients -j` (get `at`/`size` for the window by `class`) piped through `python3 -c "import json,sys; ..."` to extract geometry, then `grim -g "x,y WxH" out.png`, then `read` the png (image gets decoded inline) — much faster than blind trial-and-error on rendering bugs.
